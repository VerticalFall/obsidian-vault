### P-20260808-01 · 微信 AI 机器人：CowAgent 部署 + GitHub 读写插件（读取全部 / 写入收件箱）
- 类型：功能升级
- 现状与问题：知识库目前只在 PC 本地可读写——人不在电脑前就无法查询、无法记录（观测事实）；远程备份（vault-backup）是每周一单向 push，没有任何"远程入口"（观测事实：`weekly-backup/SKILL.md` 仅定义 push 方向）。
- 影响面：知识库可及性（异地查询/记录）；数据安全边界（机器人凭证是新的泄漏面）。
- 载体选型结论（用户选定，PM 评估认为合适）：
  - CowAgent 是 chatgpt-on-wechat 的官方继任（v2.0.0 起改名），国内生态最成熟的开源项目之一；
  - 原生支持个人微信渠道 + 插件/工具系统 + **MCP 协议**——GitHub 集成无需从零造轮子；
  - 支持 Linux 一键脚本 / Docker 部署，适合服务器环境。
- 改进方向与方案：
  1. **部署**：朋友内网服务器（用户选定）跑 CowAgent（Docker 或一键脚本）；机器人服务器只需**出站**访问 `api.github.com` + 大模型 API（DeepSeek/Claude 等），手机/PC 无需访问该服务器——同步链路走 GitHub 中转，与 VPN 无关；
  2. **渠道**：个人微信接入（chatgpt-on-wechat 系第三方协议，标注封号风险，见下）；
  3. **GitHub 凭证**：细粒度 Personal Access Token，**仅授权 `VerticalFall/obsidian-vault` 单仓库**（contents 读全部 + 写收件箱 + 创建提交），不授权其他任何仓库；
  4. **GitHub 读写插件**（本次开发物，方案二选一）：
     - 首选：**自写轻量工具插件**——读任意路径直接放行；写操作**仅允许 `01_内容系统/知识库/inbox/`**（沙箱校验，其他路径拒绝），写文件命名 `微信-YYYYMMDD-HHmm.md`。约 50-100 行代码，权限控制最精确；
     - 备选：官方 GitHub MCP server（零开发），但写入路径限制粒度弱，需靠提示词约束——不推荐单独使用；
  5. **收件箱目录约定**：`01_内容系统/知识库/inbox/`（在 vault-backup 备份范围内、不在每日日报子仓库内，避免与 Actions 冲突）；机器人写入的内容每天随 P-02 同步 pull 回本地，由用户/本地流程确认后入库；
  6. **机器人能力边界**：查询笔记、搜索知识库、汇报系统健康（读 `_告警摘要.md`）、记录想法到收件箱；不直接修改既有笔记。
- 优先级：P1
- 状态：待执行（依赖 P-20260808-02 的收件箱同步落地）
- 验收标准：
  1. 微信里对话"查《漫步华尔街》核心观点"能返回内容（读取✅）；
  2. 让机器人"记下某想法"→ 远程 `inbox/` 出现新文件 → 本地 pull 后在 Obsidian 可见（写入+同步✅）；
  3. 负测试：明确让机器人修改 `inbox/` 之外的文件 → 被拒绝（沙箱✅）；
  4. 凭证为细粒度 PAT，仅 obsidian-vault 单仓库（审计✅）。
- 风险与诚实标注：
  - **个人微信封号风险**：CowAgent 微信渠道基于第三方协议 hook，违反微信用户协议，账号可能被限制——用户已知情选择；备选渠道是企业微信（官方，随时可切换）；
  - **Agent 模式 token 消耗**：CowAgent 的 Agent 形态比普通对话耗 token 多，按量计费需预算；
  - **朋友服务器可信环境**：CowAgent README 明确提示"仅在可信环境部署"——通过凭证最小化（单仓库 PAT）+ 收件箱沙箱缓解；部署前需确认朋友服务器出站可达 github.com；
  - **未核实项**：CowAgent 个人微信渠道的登录方式细节（扫码/hook 协议版本）需在部署时按其文档核实。

### P-20260808-02 · 知识库每日双向同步（本地 ↔ vault-backup）
- 类型：链路
- 现状与问题：vault-backup 目前仅每周一由 `weekly-backup` 技能单向 push（观测事实）；远程产生的改动（机器人收件箱、手机端）没有任何机制回到本地；本地与远程的冲突策略无约定。
- 影响面：P-01 机器人功能的前置依赖；数据一致性（双向不同步 → 两边漂移）。
- 改进方向与方案：
  1. **新增 `sync-vault.ps1`**（放 `01_内容系统/系统/`，复用 `pull-reports.ps1` 的模式）：对 vault 根备份仓库执行——`git pull --ff-only`（远程→本地）→ 若有新内容 `git add -A && commit && push`（本地→远程）→ 全程写日志；
  2. **Windows 计划任务**：每天 2 次（09:00 / 21:00）+ 登录时触发，`StartWhenAvailable`（与现有 pull-reports 任务同一套机制）；
  3. **冲突策略（架构约定，不自动覆盖）**：本地为权威。pull 用 `--ff-only`；失败时先 `git stash` → pull → `stash pop`；仍冲突则**中止并告警**（写日志 + 通知），绝不自动覆盖任一方数据。远程写入面限制在 `inbox/`（P-01 约定），同文件双写概率≈0；
  4. **weekly-backup 技能调整**：从"每周一必须跑"降级为"每日同步已覆盖，周一快照作为兜底/存档节奏保留"（技能描述更新）；
  5. **每日日报子仓库不受影响**（`.gitignore` 已排除；其自身链路独立运行）。
- 优先级：P1（机器人功能前置；非系统停摆）
- 状态：待执行
- 验收标准：
  1. 本地改文件 → 计划任务 push → 远程 vault-backup 可见（本地→远程✅）；
  2. 在远程手工提交一个 `inbox/` 文件（模拟机器人写入）→ 计划任务 pull → 本地 Obsidian 可见（远程→本地✅）；
  3. 连续 3 天无人干预自动跑通，日志无异常；
  4. 人为制造冲突时：任务中止并告警，**不覆盖任何数据**（冲突保护✅）。
- 依赖：P-01 的收件箱目录约定（目录先约定，P-02 的验证才完整）；P-02 本身可先行实施。
