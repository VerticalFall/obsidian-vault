### P-20260923-01 · 路由输出截断致选题池断供 6 周

**链路 · P0 · 待验收**

#### 要解决什么

（观测）`_选题池.md` 🔥 区自 2026-08-10 起恒为 0 条，🌿 区为空，归档区从 103 涨到 152 条；L1 健康检查连续 43 天报「3 条(🔥0 🌿0 💤3)」。

（观测）根因是**输出预算截断**：`run_daily_router.py` 让模型在**一次生成**里同时产出「路由日志正文」+ `===TOPIC_POOL_UPDATES===` 选题池表格行 + `===TOPIC_UPDATES===`。路由日志正文（每个选题含来源/锚点/框架/传播分/角度/merge_hint）本身就写掉数千字，`max_tokens=8000` 耗尽后模型在「⭐ 高优先级选题」段之后停止。实测：

| 路由日志 | 字符 | 区完整度 |
|---------|:---:|---------|
| 2026-08-21 / 09-03 / 09-04 | 4458 / 5491 / 6750 | 六区齐全 |
| 2026-09-23 | 2266 | 只有 ⭐ 区，末句「而 123 条命是故事的」未写完 |
| 2026-08-24 | 698 | 只有 ⭐ 区 |

（观测）第二个隐藏缺陷：`## 普通选题` 区在 prompt 里被定义为**表格**（`| # | 选题 | 来源 | 得分 |...`），而解析逻辑只认 `### NN.` 分块，因此该区的内容**在任何解析器下都读不到**。

（观测）第三个缺陷：日期计数更新用 `re.sub(r"[^0-9]", "", 标题行)` 取数字，会把日期本身吸进计数（`### 08-09` → `（80 条）`）。

（推测）2026-08-11 的 `deepseek-v4-pro → v4-flash` 切换（提交 `af56bd5`）使输出预算更紧张，截断概率显著上升——与 8 月路由日志天数骤降（7 月 23 天 → 8 月 13 天 → 9 月 3 天）时间吻合，但未取得模型侧证据，标为推测。

#### 方案

1. 新增 `.github/scripts/extract_topic_pool.py`：从路由日志**确定性解析**选题池行（标题/钩子/角度/来源/锚点/框架/传播分/merge_hint/观点信号），不再依赖模型的第二段输出。
2. `run_daily_router.py`：选题池改由提取器产出；prompt 移除 `POOL_UPDATES`/`TOPIC_UPDATES` 段要求（省下的预算留给路由日志正文）；`## 普通选题` 区统一为 `### NN.` 格式；`max_tokens` 提为可配置常量（默认 8192，贴合 API 侧的保守上限，不靠加大预算解决截断）。
3. 新增 `detect_truncation()`：缺区、末尾悬空即打印 `WARNING`，截断不再静默。
4. 新增跨天去重 `dedupe_topics()`：实体重叠（≥2 个高信号实体）+ 字符集相似度双判，泛用词（ai/buy/openai 等）入停用词表，避免误杀。
5. 修正日期计数逻辑（只数本日期组数据行、排除表头行）。
6. `sync-reports.yml`：补 `ROUTER_MAX_TOKENS: "8192"`。

#### 验收标准

- [x] 提取器能从未被修改的历史截断日志（`_路由/2026-09-23.md`）恢复出完整选题
- [x] 跨天/当日重复选题被去重，且不误杀不同选题（6 条中只合并 1 条）
- [x] 截断日志被检出并打印 WARNING；完整日志不误报
- [x] 选题池写入正确：新建日期段置顶、计数等于实际数据行数、同日重跑不重复建段
- [x] 日期计数不再被日期数字污染（`### 08-09（10 条）` 不被改写）
- [x] 离线自测 16 项全通过（`python _test_router_pool.py`）
- [ ] **线上验证**：部署后连续 3 天 `_选题池.md` 🔥 区有新增条目（待 push 后观察）

#### 验证记录（2026-09-23）

- `python _test_router_pool.py` → 16 项 PASS（含真实截断日志解析、去重精度、写入断言）
- `python -m py_compile` 全部脚本编译通过
- 提取器对 5 份近期路由日志（08-15 后）产出 12 条选题，完整性过滤后 11 条
- 未推送远程，线上效果待验证

<details><summary>风险 / 方案细节</summary>

- **不提高 max_tokens 到 API 上限之上**：DeepSeek API 对模型输出长度有限制，设过头会让整个请求 400 失败（第 85-93 行步骤 `continue-on-error: true` 会静默吞掉），在没有 Key 可实测的情况下等于拿主链路赌。改为从结构上省预算。
- **去重阈值保守**：宁留重复不误杀。同一事件不同措辞（`Nvidia 129 亿美元收购 Hugging Face` vs `NVDA 129 亿美元买 HF`）实体重叠后判定为重复；不同选题相似度普遍 <0.2，分离带很宽。
- **提取失败不静默**：解析不到任何选题时打印 `ERROR` 并跳过选题池更新（旧逻辑静默跳过，是 6 周无人发现的原因之一）。
</details>

### P-20260923-02 · 本地日报同步失效 38 天（CRLF 阻塞 ff-only）

**链路 · P0 · 待验收**

#### 要解决什么

（观测）根仓库与本地均正常，但 `01_内容系统/知识库/每日日报/` 连续 38 天未拉到上游提交（本地停在 08-16，远程已到 09-23）。`.scripts/pull-reports.log` 每天 13:00 重复同一错误：`error: Your local changes to the following files would be overwritten by merge: _选题池.md` → `exit=1`。

（观测）9 个文件在工作区被改成 CRLF（`git diff --stat` 为空、`--ignore-all-space` 为空，证明**只有换行符差异、无内容改动**）。上游这些文件也有改动，`git pull --ff-only` 因此拒绝执行。

（观测）`系统/scripts/sync-vault.ps1`（根仓库）带 `stash → pull → pop` 兜底所以不受影响；`每日日报/.scripts/pull-reports.ps1` 只有裸 `pull --ff-only`，没有兜底——**同源缺陷只在一侧被修过**（与 [[2026-08-11-改进提案]] 记录的 08-09 故障同类，当时修的是内容分叉，这次是换行符）。

#### 方案

1. 本地处置（已完成）：`git stash` 保底 → `git pull --ff-only`（38 提交落地）→ 验证 diff 为空后 `stash drop`。
2. 建议后续：`pull-reports.ps1` 补 `stash → pull → pop` 兜底，与 `sync-vault.ps1` 对齐（本提案暂未实施，避免在批准前扩大改动面）。

#### 验收标准

- [x] 本地 `每日日报/` 与 `origin/main` 同步（`git status` 显示 `## main...origin/main`，无 behind）

### P-20260923-03 · 每日精选产出层（承接 P-20260811-02）

**功能升级 · P1 · 待验收**

#### 要解决什么

（观测）用户核心诉求是「把各类信息结合 → 提炼当天最有用的数据与信息 → 做成公众号文章」。现有链路里**没有任何环节产出"一份成品"**：四源按源分文件，路由日志是筛选结果，用户每天要打开 5 个文件才拼得出全貌。

（观测）`2026-08-11-改进提案` 的 P-20260811-02「每日专属新闻报告（统合所有源）」即此需求，立项 6 周状态仍为「待执行」。

（观测）产出层缺失导致系统"在跑但没结果"：公众号最后发布为 2026-07-22，之后 2 个月无新文，而健康检查**没有任何一项**能发现这一点（6 项全部只盯采集与筛选）。

#### 方案

1. 新增 `.github/scripts/render_daily_digest.py`：读当日四源 + 路由日志 → 单次 DeepSeek 调用 → `_每日精选/YYYY-MM-DD.md`，四区结构：今天最重要的 5 条 / 数字速览 / 领域速览 / 今天可写。
2. 输出预算取保守值 4096（本产物 900-1300 字，不需要长预算）；prompt 内嵌硬性要求：数字必须来自材料、不许推算编造、材料缺失写"今日无"、禁止评论腔填充句。
3. 新增 `validate_digest()`：缺区 / 数字速览无数字 / 正文过短 / 末尾截断 → 打印 WARNING。
4. Action 步骤插在路由之后、健康检查之前，使健康检查可一并体检。
5. 新增技能 `01_内容系统/系统/技能库/daily-digest/SKILL.md` 作为本地手动入口。
6. 技能库 README 更新为 11 个技能。

### P-20260923-11 · 思考模式默认开启，吃光短预算调用

**链路 · P0 · 待验收**

#### 要解决什么

（观测，官方文档）DeepSeek 思考模式文档明确：「**思考模式默认打开，且 effort 默认为 `high`**」。思维链（`reasoning_content`）与正文**共用 `max_tokens` 预算**。

（观测）本仓库 **5 个脚本、7 个 LLM 调用点**全都没有声明 `thinking` 参数，因此在默认开启思考模式的情况下运行：

| 脚本 | 调用点 | max_tokens | 风险 |
|------|--------|:---:|------|
| `render_xtweets.py` | 语种判断 | **100** | 思维链一展开就永远轮不到正文 → 必然失败 |
| `render_followbuilders.py` | 播客摘要 | **300** | 同上 |
| `render_xtweets.py` | 翻译 | 2000 | 预算被思维链白吃 |
| `render_followbuilders.py` | 翻译 | 2000 | 同上 |
| `run_daily_router.py` | 路由 | 8192 | 思维链挤掉路由日志正文 → **截断的另一成因** |
| `render_daily_digest.py` | 精选 | 4096 | 同上 |
| `run_weekly_distill.py` | 蒸馏 | 12000 | 同上 |

（观测）**这解释了翻译为什么是「0/N」而不是「部分成功」**：100/300 token 的调用在思考模式下拿不到任何正文，属于 100% 失败。P-20260923-09 修的模型名是必要条件，思考模式是另一半原因。

（观测）附带发现：思考模式下 `temperature` **不生效**（文档明示"设置参数不会报错，但也不会生效"），因此各脚本写的 `0.1 / 0.3 / 0.4` 从未起作用。

（推测）路由 90% 失败率中"完全无产出"的那部分，可能也与此相关（思维链耗尽 8192 预算 → `content` 为空 → 脚本抛错 → 当日无日志）；但这属于**推测**，需线上验证，不作为结论。

#### 方案

1. 7 个调用点全部显式声明 `"thinking": {"type": "disabled"}` —— 这些任务都是**格式固定的结构化产出或纯转换**，思维链无增益。
2. 各调用点写明关闭理由，尤其短预算的两处（100/300 token）。
3. 扩展 `_test_model_names.py`：要求每个 `max_tokens` 调用点都显式声明 `thinking`（正则计数比对），防止新增调用点漏声明。
4. 新增 `_test_request_body.py`：**拦截 `urlopen`、解析真实出站 JSON**，断言 `thinking.type == "disabled"`、模型名正确、必需字段齐全 —— 源码正则会说谎，出站报文不会。

#### 验收标准

- [x] 7 个调用点全部声明 thinking 且为 disabled
- [x] 源码级守卫：`declared >= call_sites` 对 5 个脚本逐一断言
- [x] 报文级验证：跨 5 个真实出站请求体断言 thinking 关闭、模型名正确
- [x] 守卫能真的抓出问题（新增调用点未声明时会失败）
- [ ] **线上验证**：push 后 🔴「翻译成功率 0/N」消失，且路由/精选产出变完整（最硬证据）

#### 验证记录（2026-09-23）

- `python _test_model_names.py` → 11 项 PASS，逐个脚本断言 `declared/call_sites`（router 1/1、distill 1/1、digest 1/1、xtweets 2/2、followbuilders 2/2）
- `python _test_request_body.py` → 12 项 PASS。实测出站 JSON 示例（路由）：
  `keys=['max_tokens','messages','model','temperature','thinking']`，`thinking={'type':'disabled'}`，`model='deepseek-flash'`
- 跨 5 个场景断言：全部请求体 thinking 关闭、模型名集合为 `{'deepseek-flash'}`
- **未验证**：真实 API 下的产出变化（本地无 Key）。依据是官方文档的默认值说明 + 出站报文已确认携带关闭参数，属**强推断**，最终以线上 🔴 消失为准

<details><summary>风险 / 方案细节</summary>

- **关闭思考会降低复杂判断的质量吗**：本仓库的 LLM 用途都是"按固定格式整理/翻译已筛好的材料"，不是开放推理。路由的"框架适配"判断确有推理成分，但它有明确的评分标尺作为脚手架，且旧版本（未声明 thinking 时）也在跑。若线上发现路由选题质量下降，可单独给路由开 `thinking: enabled` 并同时把 `ROUTER_MAX_TOKENS` 提高以容纳思维链 —— 两者必须同改，这正是本提案要防的坑。
